## 1. Problem

The owner's request, in substance: *add multiple folders and files to a corpus, in the formats a researcher or student actually uses (Word, Excel, CSV, PDF, PowerPoint, OpenDocument, EPUB, RTF, and programming files such as Python, Java and LaTeX). Browse folders and subfolders. Select a whole folder, or several files from different folders. Ask a question, and get an answer that comes only from the selected files.*

Today's corpus cannot do this:
- **Structure.** The corpus is flat. Folder uploads keep basenames only (`corpus/page.tsx:177-186`).
- **Formats.** Only PDF, HTML, Markdown and plain text are accepted (`documents.py:34-55`).
- **Scope.** Retrieval has no selection argument: the `Corpus` port is `search(query, max_results)` / `read(url)` (`ports.py:83-99`).

## 3. Goals, non-goals, anti-goals

**Goals**
1. A user can organize documents in folders and subfolders, select any mix of folders and files, and start a research run over exactly that selection.
2. Every piece of evidence and every citation in such a run comes from the frozen selection. This is enforced in the store, checked again when the run is saved, and recorded in the bundle.
3. Two separate guarantees, each enforced by itself:
   - **Only selected files**: what the evidence may come from.
   - **Offline**: where model calls may go.
4. The formats in §10 are accepted under the citation-grade rule: every accepted format can be quoted exactly and located.
5. Both hosts behave the same. B-1 to B-7 are fixed.

**Non-goals for 3.1**
- OCR for scanned PDFs and images (OWNER: not chosen).
- Saved named collections (ADOPTED).
- A chat surface for selections (OWNER: the answer surface is a research run).
- Desktop linking of local folders in place (CLAUDE'S CALL: upload-by-copy on both hosts).
- Cell-level highlighting, spreadsheet formulas, merged-cell semantics.
- Bundle format v3.

**Anti-goals.** Any of these would make the release a failure even if every feature works:
- Formats or folder UI shipped while selection or project isolation is incomplete.
- A "not in your files" outcome that falls back to the model's own knowledge.
- Any copy that claims more than the code enforces.
- A change that a 3.0.x binary or verifier cannot read. That would silently make this release a major one (`RELEASE.md:256-258`).

## 5. Capability definition

**In scope, as behaviour**
- Upload files or whole folders on web and desktop, including dropped folders. Relative paths are kept as folders.
- Browse folders. Create, rename, move and delete folders. Move documents between folders.
- Select with folder checkboxes (tri-state) and file checkboxes across folders, then **Ask about these files**. That opens the run form with the selection attached and **Only selected files** switched on. **Offline** is a separate switch on the same form.
- The run page shows what the run used: the selection (N files, by path), the corpus version, and which of the two guarantees held.
- Clicking a citation opens the file at its location: page, sheet and row, slide, or lines.
- The bundle records which document versions the run was allowed to use. The 3.1 verifier checks that every corpus source is one of them.

**Out of scope, as behaviour**
- No question can be asked across projects.
- No selection outlives its run.
- The app does not watch a folder on disk.
- Scanned pages are refused as before. Partly scanned PDFs are accepted with the missing pages named (B-5 fix, §10).

## 6. The two guarantees

### 6.1 Only selected files (evidence scope)
- **Definition.** Every search result, every read, every piece of evidence and every cited source of the run is a document version in the frozen selection. Web search and web reads are refused, as in today's corpus mode.
- **Enforced at**
  - the store/port, by `ScopedCorpus` (§8.4);
  - save time, by the persist check (§8.5);
  - verify time, by the bundle check (§8.6).
- **Not a network claim.** Run form copy: *"Evidence comes only from the files you selected. Your question and excerpts from those files are sent to the model provider you've configured."*
- **Recorded.** `research_runs.corpus_selection` (§8.2).

### 6.2 Offline (model locality)
- **Definition.** Every model call in the run goes to a local endpoint, and the run makes no web calls. That covers all five role routes and the embedder. Runs have no follow-up chat today, so chat is not covered. A local endpoint is `ollama:` or a `custom:` route whose base URL is local.
- **Enforced** by one pure function in `research_engine`, `offline_violations(run_config) -> list[str]`. It is built on `llm_factory` route parsing, `map_local_host` and `is_local_endpoint`, so no third copy of the locality rule appears.
  - Both hosts call it before the run starts: the create handler in `run_lifecycle.create_run` and the resume path. A violation refuses with 422 `offline_unavailable`, naming each role and its route.
  - It is called again inside the executor's first `get_llm` as a backstop.
- **Recorded.** New column `research_runs.offline` (bool, server default false).
- **Copy.** *"Offline: every model runs on this computer. Research refuses to start if any model is set to a cloud provider."*
- Offline does not require Only selected files, and the reverse holds too. With Offline on and no selection, the run uses the whole project corpus, frozen.

## 7. Data model

### 7.1 Corpus SQLite: additive, through `CorpusStore._migrate`

| Change | Shape | Downgrade (a 3.0.2 binary opening this file) |
|---|---|---|
| `corpus_folders` (new) | `id TEXT PK` (uuid4), `parent_id TEXT NULL` (FK to the same table, `ON DELETE CASCADE`), `name TEXT`, `created_at`; `UNIQUE(parent_id, name)`, with a partial index for root names | Ignored: 3.0.2 never queries it |
| `corpus_memberships` (new) | `id INTEGER PK`, `doc_key TEXT`, `folder_id TEXT NULL` (NULL means the root, `ON DELETE CASCADE`), `display_name TEXT`, `added_at`; `UNIQUE(folder_id, display_name)`, `INDEX(doc_key)` | Ignored |
| `corpus_documents.segments` (new, nullable) | JSON `[[start, label], …]`, sorted by start; NULL for legacy rows | Ignored. 3.0.2 selects named columns only (`corpus.py:146-182`), unverified for every query, so a test must confirm it (AC-24) |
| `corpus_documents.extraction_mode` (new, nullable) | `'verbatim'` or `'linearized'`; NULL is read as `'verbatim'` | Ignored |
| `corpus_documents.kind` | New values (§10) | **Risk:** a 3.0.2 server preview or download of a new kind falls back to an attachment (`document_headers._MEDIA_TYPES`). That is acceptable but must be tested (AC-24) |
| Kept unchanged | `UNIQUE(filename, sha256)` and `UNIQUE(doc_key, version)` | Must stay: 3.0.2's `_migrate` re-runs `CREATE UNIQUE INDEX IF NOT EXISTS` on every open (`corpus.py:302-305`), so data that violates them would make 3.0.2 fail to open the file |

- `_SCHEMA_VERSION` becomes 3. It is recorded for new stores and, as today, never rewritten on existing rows.
- Legacy documents get no membership row. **A document with no membership is listed at the root.** No backfill is needed.

**Duplicate semantics.** The same bytes and the same filename uploaded into a second folder return the existing document (`corpus.py:413-421`) and add a second membership. The same filename with different bytes in two folders is two documents; that already works.

**Folder delete.** It removes the folder, its subfolders and their memberships. A document left with **no** membership is deleted, along with all its versions and their chunks. The UI asks for confirmation and states how many files will be deleted.
- Runs that cited a deleted document keep their persisted evidence (the `evidence` table holds the snippets). Their `read()` returns a distinct `document_unavailable` error, never an empty success.
- Neither the run report nor its bundle depends on the original still existing. This is the "explicit behaviour for unavailable originals" requirement.

**Rename and move** change only folder rows, so ids stay stable.

### 7.2 Relational (Postgres through Alembic 0028; desktop.sqlite through `create_all` plus column sync)
- `research_runs.corpus_selection` JSON, NULL. The shape is in §8.2.
- `research_runs.offline` BOOLEAN NOT NULL, server default false.
- `research_runs.grounding_report` JSON, NULL (§9.6).
- Both are additive and nullable or defaulted (`sidecar.py:476-487` rule), and no CHECK changes. A 3.0.x binary ignores them.

### 7.3 Desktop per-project files (fixes B-1)
- `_DesktopCorpusLocator` resolves `corpus_<project_id>.sqlite` under the app data directory, as the server does. Its `delete`/`paths_to_delete` delete the files.
- **Legacy flat store (D-17).** On first 3.1 launch, an existing `corpus.sqlite` that holds rows is migrated into a new project, **"Documents from before 3.1"**. Nothing is copied into any other project.
  **Ownership has exactly one authority point.**
  - A new desktop-only key-value table `app_meta` in `desktop.sqlite` holds `corpus_layout`, either `shared` (absent means `shared`) or `per_project`. None exists today; `create_all` adds it, and because it is desktop-only it gets no Alembic migration.
  - The desktop locator reads `corpus_layout` and resolves **only** the stores that layout names:
    - **`shared`:** only `corpus.sqlite`;
    - **`per_project`:** only `corpus_<project_id>.sqlite`. The legacy and backup files are never resolved, so no code path can open them for writing.
  - **The commit that sets `per_project` is the moment the new project becomes authoritative.** Before it, the shared store is the only writable store. After it, the per-project store is. There is no instant at which two writable stores can diverge.
  - The migration runs at sidecar start **before the HTTP server accepts requests**, under a file lock (`corpus.migration.lock`), so no upload, delete or run can touch either store mid-migration.

  **Steps.** Each step is re-entrant: it checks what is already on disk before acting.
  1. **Back up.** Copy the live `corpus.sqlite`, including its WAL, with SQLite's online backup API to `corpus.legacy-3.0.sqlite.tmp`, then fsync it and rename it to `corpus.legacy-3.0.sqlite`.
  2. **Verify the backup.** It counts as *verified* only if **all** of these hold, comparing the backup with the live store:
     - `PRAGMA integrity_check` returns exactly `ok`;
     - `PRAGMA foreign_key_check` returns no rows;
     - the row counts of `corpus_documents`, `corpus_chunks` and `corpus_meta` are equal;
     - the multisets of `(id, doc_key, version, sha256, superseded_at)` are equal;
     - for every document with a stored `blob`, `sha256(blob)` recomputed equals its `sha256` column, in both files;
     - `corpus_meta.corpus_id` is equal.

     Any failure stops the migration. The app keeps the shared layout with a visible warning, and records the failed check by name.
  3. **Build the project store from the verified backup**, not from the live file: copy it to `corpus_<legacy_project_id>.sqlite.tmp`, check it against the step 2 conditions, then rename it to `corpus_<legacy_project_id>.sqlite`. The project id is fixed in advance and stored in the lock file, so a retry reuses it.
  4. **Commit (the authority point).** One `desktop.sqlite` transaction does all of the following:
     - inserts the project row;
     - sets `corpus_layout = per_project`;
     - writes `corpus_legacy_migration = {project_id, corpus_id, documents, chunks, backup_sha256, completed_at}`.
  5. **Retire the shared file.** Delete `corpus.sqlite` and its WAL/SHM. The backup is never deleted by the app.

  **Recovery on every launch.** Each state the migration can be left in has one defined action:

  | State found on launch | Action |
  |---|---|
  | `shared`, no backup | start at step 1 |
  | `shared`, `.tmp` backup only | discard the `.tmp` backup and redo step 1 |
  | `shared`, verified backup, no project store | step 3 |
  | `shared`, project store present (the crash came before the commit) | the store is unreachable, so delete it and redo step 3 |
  | `per_project`, `corpus.sqlite` still present | it is unreachable under this layout, so delete it (step 5) |
  | `per_project`, project store missing or failing the step 2 checks | **do not serve the project.** Rebuild it from the backup and re-check. If that fails too, show the error and leave the backup untouched |

  **What a copy preserves.** Copying the whole file keeps every document id, `doc_key`, version, `sha256`, chunk and embedding, and the `corpus_meta.corpus_id`. Every historical `corpus://<id>#chars=…` reference therefore stays byte-identical. Because `corpus_documents.id` is a uuid per **version** (`corpus.py:146-170`), an id names one exact version.

  **Downgrade.** A 3.0.x binary reads `corpus.legacy-3.0.sqlite` only if the user renames it back. The release note says so, and G-3 shows it working.
- **Historical citations across projects.** Runs and sessions in other projects that cited legacy documents keep their persisted evidence (the `evidence` table holds the snippets), so their reports and bundles still verify. Reopening a cited document goes through one narrow route, `GET /runs/{id}/cited-documents/{document_id}` (and its session twin), under these rules:
  - **The caller must own the run.** Project membership is checked for the run's own project, not for the legacy project.
  - **`document_id` must be one the run itself recorded** as a corpus source, by id, which pins the version. Where the run recorded a `sha256` (3.1 runs), the stored document's `sha256` must match it too.
  - **The store is resolved by the run's recorded `corpus_id`**, never by a project id the caller supplies.
  - **The route returns that one version's extracted text and original only.** It offers no listing, no search, no other id and no other version of the same `doc_key`. Every other id is 404 with the same body as a missing document.

  This grants no access to the legacy project. A run can reopen exactly what it quoted, and nothing else (AC-27, AC-37).
- **Telling users.** On first launch after the migration, a one-time notice says: *"Your N documents from before 3.1 are now in the project 'Documents from before 3.1'. Projects no longer share documents. Add a document to another project by uploading it there."* The project's description repeats it, and so does the release note.
- Documents added in 3.1 are invisible to a downgraded binary. This is documented, not a failure.
- **Desktop chat "My corpus" scope** becomes per-project for free. That fixes C9.
- `test_desktop_contract_gaps.py:199-219` is inverted: it currently asserts the leak.

### 7.4 Versioning conclusion
- Every schema change is additive, and no bundle format change ships (D-12). Under M0.03 that makes this release **3.1.0**.
- Two things would turn it into 4.0.0, and must be refused in review:
  - any CHECK widening;
  - any change to the two unique indexes.

## 8. Selection lifecycle

### 8.1 Request
`CreateRunRequest.corpus_selection: CorpusSelectionRequest | None`, where `CorpusSelectionRequest = {folder_ids: list[str], doc_keys: list[str]}`, each capped at 5,000.
- `corpus_selection` set means corpus mode is on. Sending `corpus_mode: false` with it is a 422.
- `corpus_mode: true` with no selection keeps today's meaning, whole corpus, but now **frozen** like any selection. One code path.

### 8.2 Freeze (at `create_run`, inside the shared lifecycle, so both hosts get it)
- **Resolution.**
  1. Expand folders recursively to memberships, then to `doc_key`s, and take their union with `doc_keys`.
  2. Map each key to its **current** version, excluding `origin='generated'`.
- **Stored** in `research_runs.corpus_selection`:
  ```json
  {"requested": {"folder_ids": [...], "doc_keys": [...]},
   "resolved": [{"document_id": "...", "doc_key": "...", "version": 1, "sha256": "...", "filename": "...", "path": "Thesis/Ch2/data.xlsx"}],
   "corpus_id": "...", "corpus_version": 17}
  ```
- **Errors**, each distinct and named:
  - 422 `selection_empty`: nothing was requested.
  - 422 `selection_resolved_empty`: the folders hold no current documents.
  - 404 `selection_not_found`: an id is not in this project. The response does not say which id, so it cannot be used to probe for documents in other projects.
- **Frozen.** Resume and the plan gate read the row and never resolve again. The selection is a `CONTROL_PLANE_FIELDS` entry (`test_prompt_override_reach.py:42-51`), never a `PREFERENCE_FIELDS` entry.

### 8.3 Row → RunConfig
- New field `RunConfig.corpus_allowed_ids: frozenset[str] | None`.
- It is set in **both** run builders: `run_execution::run_config_for_run` and `sidecar::_drive_run`.
- The session builders (`pipeline_runner::_run_config_for`, `sidecar::_drive_session`) leave it `None`, by design (D-8). AC-12 asserts this.

### 8.4 Enforcement in the store and port
- `research_engine/corpus.py::ScopedCorpus(inner, allowed_ids)` implements the `Corpus` protocol:
  - **`search`** calls `inner.search(query, k, document_ids=allowed_ids)`. The new keyword filters `_search_sync` **and** its empty-result diagnostics (`corpus.py:575-626`), so "no match in your selection" is reported as that, not as "wrong embedding model". The filter uses a temp table or `json_each`, never a raw `IN (…)`, because the parameter limit was not measured.
  - **`read`** parses the URL and refuses an id outside `allowed_ids` with the error string `outside_selection`. Superseded versions are readable **only** when they are in the frozen set.
- **Installed by one shared function**, `run_execution.corpus_port_for_run(locator, run)`, which both hosts call:
  - `run_execution._corpus_port` (server, `:615-634`);
  - `sidecar._drive_run` (desktop, which today installs the port for every run, `:1615-1621`).
- **Fixes B-4:**
  - the desktop installs the port only for corpus runs;
  - `tools.read_webpage` resolves `corpus://` only when `corpus_mode` is on (`tools.py:111-117`).
- **The cache can't be a bypass:** the corpus branch in `retrievers.search` runs before the cache (`retrievers.py:92-96`). AC-4 pins this so a refactor cannot reorder it.

### 8.5 Defence in depth when the run is saved
- `run_lifecycle.record_evidence` parses the document id off each corpus source's `corpus_document_id`. That column holds the fragment too: C3, `run_lifecycle.py:345-347`.
- If any id is not in `corpus_selection.resolved`, the run fails with `selection_violation` and the offending ids are logged under `run_id`. Nothing is quietly dropped.
- This should never fire. If it does, it is a P0 alarm, not a warning.

### 8.6 Provenance
- **`GET /runs/{id}`** exposes `corpus_id`, `corpus_version`, `corpus_selection` (resolved paths) and `offline`. This fixes B-7.
- **Bundle (stays v2, D-12):**
  - each corpus entry in `sources` gains `document_id`, `doc_key`, `version`, `sha256`, `path` and `extraction_mode`;
  - `trace` gains one entry, `{"event": "corpus_selection", "resolved": [...], "corpus_id", "corpus_version", "offline"}`.
- **Verifier.** `verify_bundle` gains a `corpus_selection` check that applies only when that entry is present: every corpus source's `document_id` is in it.
  - A 3.0.x verifier still verifies these bundles, because the hash rules are unchanged. It simply does not run the new check. `docs/15` says so.
  - Both fields are already covered by `bundle_hash`, so the provenance cannot be edited without breaking verification. This avoids the review's "opaque field" objection: the entry is named, hashed and checked.

### 8.7 Mid-run changes
- **A selected document superseded mid-run.** The run keeps using its frozen version, which stays readable because it is in the set.
- **A selected document deleted mid-run.** Reads return `document_unavailable`, and evidence already gathered stands.
- **A folder renamed mid-run.** No effect; the selection is ids.

## 9. Grounding contract for selection runs (fixes B-3; D-18)

**The requirement (OWNER, Q2).** Every substantive factual claim in the answer of a selection run is supported by the selected documents. A claim that cannot be supported is never presented as a verified conclusion. Unsupported claims are kept out by regenerating the affected text, not by deleting sentences after generation, because deletion can leave broken logic, dangling references or a conclusion whose premises are gone. If the selection cannot answer the question, the run says so.

**What it builds on, and what changes.** The existing fidelity pass (`graph.py:1260-1420`) is the base:
- It extracts claim sentences with `claims.split_sentences` and `claims.is_claim_sentence` (`claims.py:90,105`).
- It mechanically rejects numbers that are absent from the snippets (`_numbers_grounded`).
- It asks the critic, through the PROTECTED `critic.citation_verify`, for one YES/NO verdict per claim (`prompts.py:111-117`).
- It appends `(citation could not be verified)` to a rejected claim (`graph.py:1186`).

Four behaviours of that pass are wrong for a selection run, and §9 replaces them for selection runs only. Every other run keeps today's pass unchanged (AC-12):

| Today | Selection run |
|---|---|
| Only sentences that carry a citation are judged (`if claims.CITE_RE.search(s)`). **Uncited claims are never checked.** | Every claim is judged. An uncited substantive claim is unsupported by definition. |
| A sentence is judged as one unit, so one verdict covers every clause. | Sentences are decomposed into atomic claims first (§9.2). |
| A verifier failure keeps every citation in place (`graph.py:1386-1393`). | A verifier failure means **unmeasured**, and the run cannot finish as verified (§9.6). |
| A rejected claim stays in the text with a note. | A rejected claim is repaired out of the text (§9.4). |

None of this rests on a prompt being obeyed: `executor.main`, `critic.research` and `synthesizer.main` are user-overridable. The decomposition, verification and repair purposes are **PROTECTED** (§9.7), and the accounting is deterministic code.

### 9.1 Units the validator sees
The draft is parsed with the same line walk as `graph.py:1274-1297`.

- **Headings.** A heading is a topic label, not a claim. It is validated **as a claim** if it carries a `[n]` marker, contains a digit, or is longer than 12 words. If it then fails, it is rewritten by the repair step like any other unit.
- **Body paragraphs and list items.** Each is a unit of repair. Each one's sentences are decomposed into atomic claims.
- **Every other place a claim can hide is a unit too, and all are decomposed:**
  - **Parentheticals and appositives** stay inside their sentence, and the decomposition must cover them (the coverage check in §9.2).
  - **Bullets and nested bullets:** each item is its own unit.
  - **Markdown tables:** each body row is a unit, and each non-empty cell's assertion is a claim tied to its column header. A header row is a label.
  - **Captions:** any line starting `Figure`, `Table` or `Source:`, or an italic line directly under a table.
  - **Block quotes**, which must also match a snippet verbatim, or they are rejected.
  - **Conclusion and summary units** (§9.4).
- **The parser's coverage is itself checked.** Every non-blank line of the draft outside `## Sources` and the engine-appended blocks must belong to exactly one unit. A line that matches no rule fails the run as `grounding_unmeasured: unparsed_content` instead of escaping validation (AC-38).
- **"What your files don't cover"** (the Limitations section, renamed for selection runs). Each sentence must be a statement about the selection, not about the world. Deterministic check: the sentence names the selection ("the selected files", "these files", "none of the N files"), carries no citation marker, and contains no digit that is absent from the question. A sentence that fails the check moves into the body and is validated as a claim. This closes the exemption that lets Limitations carry model knowledge today.
- **`## Sources`**, and the engine-appended *Conflicting evidence* block: generated, not validated, as today.

### 9.2 Atomic claim decomposition
- A new PROTECTED purpose, `critic.claim_decompose`, splits each body sentence into **atomic claims**. Each claim is the smallest assertion that can be true or false on its own: one subject–predicate pair, one number, one date, one comparison.
- **Every claim names the citation markers its sentence attached to it.** A claim in a sentence that carries `[2, 5]` may draw on either source; a claim in a sentence with no marker is uncited.
- The output is structured: `{sentence_id, claims: [{text, cites: [n…], span: [start, end]}]}`, where `span` is a character range of the claim inside the sentence. **Any decomposition that fails one of these checks is treated as unmeasured for that sentence, never as supported**:
  - the spans must lie inside the sentence and must not overlap;
  - together they must cover every factual token, which means every digit, every capitalised entity and every quoted string in the sentence;
  - each `cites` entry must be a marker that actually appears in the sentence.
- **Compound sentences.** "Enrolment rose 12% in 2021 [3] and fell in 2022." gives two claims. A supported first clause cannot carry an invented second one, because each claim gets its own verdict.

### 9.3 Verification per claim

**Two separate validations, two separate counts.** Neither one implies the other, and each has its own tests.
- **Citation validation** is structural. Each `[n]` resolves to a numbered source; that source is a corpus document version in the frozen selection; and evidence for it was actually retrieved in this run. A marker that fails any of these is an `invalid_citation`, and the claim loses that citation. This check runs before any model is asked anything.
- **Claim validation** is about meaning: is the claim entailed by the snippets of its *valid* citations? A claim can have only valid citations and still be unsupported (AC-29).

**Mechanical number-and-date check.** This replaces today's verbatim `_numbers_grounded` for selection runs. It is **necessary, never sufficient**: a value that passes can still be attached to the wrong subject, which only the model verdict catches (AC-40).
- **What it extracts.** Every quantity in the claim and in its cited snippets: integers, decimals, percentages, currency amounts, quantities with units, years and full dates.
- **Normalisation.** The rules are deliberately narrow, and anything ambiguous is compared literally:

  | Representation | Rule |
  |---|---|
  | Thousands separators | `1,000` = `1000` = `1 000`. A comma is read as a thousands separator only when it is followed by exactly three digits. Otherwise, as in `1,5`, the value is compared literally |
  | Scale words | `k`/`thousand` = ×10³; `M`/`million`/`mn` = ×10⁶; `bn`/`billion` = ×10⁹ (short scale) |
  | Percentages | `12%` = `12 percent` = `12 per cent`. A ratio (`0.12`) is **not** equal to `12%` unless the snippet itself states both |
  | Units | one table of identity conversions within a dimension (`mm`/`cm`/`m`/`km`; `g`/`kg`; `ms`/`s`/`min`/`h`; `°C` only as `°C`). The claim's value must equal the snippet's after conversion. A quantity across dimensions never matches |
  | Dates | Month names, ISO `YYYY-MM-DD`, `D Month YYYY` and `Month D, YYYY` are normalised to ISO. **All-numeric dates such as `03/04/2021` are ambiguous and compared literally.** A year alone matches a full date in that year only when the claim states just the year |
  | Rounding | A claim value matches a snippet value if it equals the snippet value **rounded half-up to the claim's own precision** (`12.4%` supports "12%", but not "13%"). A claim may round a value but never make it more precise |
  | Calculated values | Differences, sums, ratios and percentage changes are allowed **only** if the decomposition states the operation in its structured `calculation` field (`{op, operands: [claim_value_refs]}`). Each operand must pass this check on its own, and the arithmetic is recomputed in code to the claim's precision. A computed value without a `calculation` is rejected as `number_not_in_snippet` |

- **Failure.** A quantity that no rule matches makes the claim unsupported (`number_not_in_snippet`), and no model opinion can rescue it (`graph.py:1376-1381`). The rules live in one pure module, `research_engine/quantities.py`, with table-driven tests of both accepted and rejected pairs (AC-39).

**Model verdict.**
- For selection runs, a new **PROTECTED** purpose, `critic.claim_verify`, replaces the YES/NO `critic.citation_verify` (which other runs keep). It judges each claim against **the snippets of all its valid citations, taken together**, and answers in a three-way format: `Claim N: SUPPORTED`, `Claim N: NOT_SUPPORTED` or `Claim N: CONTRADICTED`.
- A claim supported only by combining two sources is supported (AC-31).
- **`CONTRADICTED`** means a snippet states the opposite or a different value. It is counted apart from `NOT_SUPPORTED`, so the run page and the eval can tell "your files say otherwise" from "your files don't say".
- Any line that is not one of the three forms, or a missing line, makes that claim **unmeasured** (`malformed_response`), never supported.
- **Each citation is then judged on its own** with `critic.citation_relevance`, a new PROTECTED purpose with the same YES/NO line format: does this snippet support any part of the claim?
  - A citation that supports nothing is **removed from the claim** and counted as a `non_supporting_citation`, even when the claim is supported by the others.
  - **A citation to a relevant document that does not support the claim is therefore caught**: presence and topical relevance are not support.
- **Snippets must be in the selection.** Only snippets of evidence whose document is in the frozen selection are offered to the verifier (§8.4, §8.5). A claim whose only citations point outside the selection is unsupported. That case should be impossible, and if it reaches §8.5 it fails the run.

### 9.4 Repair, not deletion
1. **Repair.** Every unit (paragraph, list item or failing heading) that contains at least one unsupported claim is sent to `synthesizer.repair`, which is PROTECTED. It gets the unit's supported claims with their citations, and the list of rejected claims, which must not appear.
   - It rewrites the unit as a coherent passage that states only the supported claims.
   - It keeps the unit's `[n]` markers valid.
   - It must not introduce a conclusion that needed a rejected premise.
2. **Re-validate from scratch.** The rewrite instruction is never trusted as proof that unsupported content is gone. The rewritten unit is **re-parsed and re-decomposed in full** (§9.1–§9.2), and **every** resulting claim is verified again (§9.3).
   - Verdicts from before the rewrite are not reused, even when a claim's text is unchanged, because its context and citations may have changed.
   - The re-decomposition is also compared with the rejected list: a claim that normalises to the same text, after the §9.3 quantity rules, as a rejected one is rejected again without a model call, and counted as `reintroduced` (AC-36).
3. **Bounded.** Each unit gets at most **two** repair attempts. A unit still failing after two is **dropped whole**, and the report says so in place: *"A paragraph was removed: its claims are not supported by your selected files."* Dropping a whole unit cannot leave a half-sentence or a dangling `[n]`.
4. **References.** After repair, the `## Sources` list and citation numbering are rebuilt from the final text, using the existing `_number_sources` path. No orphan sources remain, and no `[n]` points at nothing.
5. **Conclusions.** A unit titled as a conclusion or summary (heading matching `conclusion|summary|overall|in short|key findings`, case-insensitive), and the report's opening summary paragraph if it has one, is **always** regenerated last, after every other unit is final, from the final supported claims only. A conclusion therefore never rests on a premise that was repaired away.
   - **A grounded premise does not make the conclusion grounded.** Each atomic claim of a regenerated conclusion is then verified by a new **PROTECTED** purpose, `critic.inference_verify`. It is given the claim, the supported claims the conclusion cites, and their snippets, and it answers `SUPPORTED` / `NOT_SUPPORTED` / `CONTRADICTED` on whether the conclusion **follows from** them without adding a new fact, a causal link, a generalisation beyond the cited scope, or a quantity.
   - A conclusion claim that fails is repaired or dropped like any other (§9.4 steps 1–3), and counted as `inference_rejected` (AC-41).

### 9.5 Insufficient evidence
- **No supported claim at all.** If, after repair, the body holds no supported claim, the run fails with `selection_no_evidence` (D-15) and the user sees: *"Your N selected files don't answer this question. Nothing was answered from outside them."* The draft is not shown as a report.
- **Partial coverage.** If the selection answers part of the question, the report keeps the supported part, and "What your files don't cover" says what is missing. The validator does not decide what is missing; it only requires the section's sentences to be statements about the selection (§9.1).

### 9.6 Accounting and the unmeasured case
- **Recorded and exposed.** Counts go to a new `research_runs.grounding_report` JSON column (nullable, Alembic 0028 alongside §7.2's columns), to the bundle as a `trace` entry `{"event": "grounding_validation", …}`, and to the run page:
  - `claims_total` and `claims_supported`;
  - `claims_rejected`, split into `uncited`, `number_not_in_snippet`, `not_supported`, `contradicted`, `reintroduced` and `inference_rejected`;
  - `claims_unmeasured`, split by cause (below);
  - citation validation, counted separately: `invalid_citations` and `non_supporting_citations`;
  - `units_repaired` and `units_dropped`;
  - `decompositions_failed`;
  - `validation_cost` (§9.9);
  - `status` and `validated_text_sha256`.
- **Every claim gets exactly one final state:** `supported`, `not_supported`, `contradicted` or `unmeasured`. The `unmeasured` state always carries a cause, one of:
  - `provider_outage` (5xx or connection failure);
  - `rate_limited` (429);
  - `timeout`;
  - `budget_exhausted` (§9.9);
  - `malformed_response`;
  - `decomposition_invalid`;
  - `unparsed_content`.

  The cause comes from the provider exception's type and status, never from the message text. "The checker couldn't run" is therefore always distinguishable from "the claim is false".
- **Unmeasured is not supported, and not unsupported either** (the P0 honesty rule). A claim the verifier could not judge — call failed, quota exhausted, malformed answer — is counted under `claims_unmeasured`, never under `claims_supported` or `claims_rejected`, and is **never presented as verified**: it goes through repair like an unsupported claim.
- **Run fails if anything is unmeasured.** If `claims_unmeasured > 0` once repair has finished, the run fails with `grounding_unmeasured`, naming the cause (for example "the critic model's quota is exhausted"). It does not reach the approval gate. A selection run's report is either fully measured or not shown.
- **No path around the gate.** An unmeasured claim cannot reach approval by any route, because the gate decides on durable state, not on an in-memory result:
  - **Gate condition.** For a selection run, `hitl_gate_node` interrupts for approval only when the persisted `grounding_report` has `status = "complete"`, `claims_unmeasured = 0`, and a `validated_text_sha256` equal to the sha256 of the report text it is about to present. Anything else routes to the failer. Approval routes (`runs.submit_report_review`) re-check the same three conditions against the row and refuse with 409 if any fails.
  - **Retry and resume.** Validation state is written in the same transaction as the validated text. A run resumed from any checkpoint before that write **re-runs validation from the start**, and a partially validated draft is never resumed as validated.
  - **Fallback.** For selection runs, the existing "verifier failure keeps every citation" fallback (`graph.py:1386-1393`) is **disabled**. There is no other model fallback for the protected purposes: a failed call is unmeasured.
  - **Caching.** Verdicts are never cached across runs or attempts. A verdict is valid only for the exact `(claim_text, snippet set, prompt sha)` it was produced for, inside one validation pass. The retriever's search cache is already bypassed in corpus mode (§8.4).
  - **Rendering.** Every surface that shows a selection run's report renders the validated text stored on the row, never the pre-validation draft held in the checkpoint: the run page, the export to `.md`/`.pdf`, the bundle `report`, and the preview. AC-42 asserts each surface by hash.
- **Not double-counted.** The eval harness rules stay as they are (`harness.py::judge_citation_support`, `benchmark.py::calc_support_rate`, which exclude unjudged claims from the denominator). `grounding_report` is the engine's own record, and the eval must not read it as a second measurement of the same thing.

### 9.9 Cost, budget and failure behaviour
- **What it costs.** Validation adds checking-model calls:
  - **Checks:** about one call per sentence for decomposition, and one per four claims each for verification and per-citation relevance (today's `BATCH = 4`). There is one inference call per conclusion claim.
  - **Repair:** at most two synthesizer calls per failing unit, each followed by a full re-validation of that unit.
- **One budget.** Every one of these calls counts against the run's existing limits, including retries and repairs: cost, wall-clock and `max_input_tokens`, through `graph._over_budget` and `_BudgetGuard.exceeded`, where `0` still means unlimited. Validation gets no separate allowance, and no limit is ever relaxed so that validation can finish.
- **Retries.** A provider retry of the same call counts too, whatever layer issues it. At most 2 retries per call, with backoff, for `rate_limited`, `timeout` and `provider_outage`; then the claims in that call become unmeasured with that cause.
- **Pre-flight estimate.** Before validation starts, the engine estimates its cost from the draft: sentence count × the calls per sentence above × the observed token sizes per call × the route's price. If a limit is set and `spent + estimate` exceeds it, the run fails **before** spending on validation, as `grounding_unmeasured: budget_insufficient`. It names the estimate, the amount already spent and the limit, so the user can raise the limit and re-run rather than pay for a validation that cannot finish.
- **Running out mid-validation.** The check runs at every call boundary, never mid-call. When a limit is crossed:
  - validation stops at the next boundary;
  - every claim not yet verified becomes `unmeasured: budget_exhausted`;
  - the partial counts are written;
  - the run fails with the failer's breach reason, naming which limit was crossed and by how much (the existing failer contract).

  No partial report is presented and nothing reaches approval. This applies equally when the limit is crossed partway through a paragraph or a repair attempt.
- **Recorded.** `grounding_report.validation_cost` holds, separately from research cost:
  - `{estimated_usd, actual_usd, calls, tokens_in, tokens_out, retries, repairs}`;
  - the failure cause, if any.

  The run page shows research cost and checking cost as two figures.
- **Providers without prices.** On `openrouter` and `custom` routes, `estimate_cost()` returns `0.0`, so the cost limit cannot protect anything there (root AGENTS.md). For those routes:
  - the pre-flight check uses `max_input_tokens` if it is set;
  - the run page says *"checking cost unknown on this provider"* instead of $0.00.
- **Small selections.** Whether a small selection still gets a useful answer within a normal limit is **measured, not assumed** (G-5).

## 10. Extraction specification

### 10.1 The contract, which applies to every format
- `extract_document` returns `(text, page_starts, kind, segments, extraction_mode)`.
  - `text` is **canonical**: deterministic and byte-identical on both hosts for pinned parser versions.
  - Chunks remain verbatim spans of it (`chunking.py:216-236`), and quotes are verified against it.
- **`segments`** is `[[start_char, label], …]`. The label of a span is the label of the last segment starting at or before `start`, plus, where useful, the last one before `end` (for example "rows 14–22"). `read()` titles become `filename — <label>`; `page` stays PDF-only.
  - Open item: `ReportView` picks its renderer from the title (audit §5, unverified claims). PR-17 must remove that coupling before the title format changes.
- **Header rows.** Where a row is unreadable without its header, the header is written **into the canonical text itself** on every row. Verbatim matching survives because the label is part of the text that is quoted.
- **`linearized`** marks any text that is a rendering of non-text structure. The UI shows "quoted from a text rendering of this spreadsheet/slide deck/notebook".

### 10.2 Per format

| Format | Ext. | Tier | Canonical text | Segments / label | Mode |

| Jupyter | .ipynb | A | stdlib `json`. Per cell: `## Cell N (markdown\|code)` + source. Text outputs (`stream`, `text/plain`) after `Output:`, truncated at 4 KB per cell. Images dropped and counted | `cell N` | linearized |

**Refused, each with a named message** (no 500s):
- encrypted or password-protected files;
- macro-only content;
- files above the size and decompression caps (§11.2);
- a scanned PDF page. A partly scanned PDF is accepted, and the image-only pages it is missing are **listed on the document**, fixing the silent `""` at `documents.py:105-108`.

**Chunking.**
- Linearized formats prefer row, slide or cell boundaries as break points.
- Code prefers blank lines. A function boundary is a 3.2 idea.
- The ~1,200-character target is unchanged.

### 11.2 Resource limits (B-5)
- **Upload size.** 25 MiB per upload, unchanged.
- **ZIP-based formats**, checked **before** parsing:
  - total uncompressed size of 200 MiB or less;
  - a compression ratio of 100:1 or less per member;
  - 10,000 members or fewer.

### 14.3 G-5: threshold form and fallback order (agreed 2026-10-25, D-22)

**Threshold form.** The owner fills in X, Y, Z and L from the PR-19 measurements, before the release candidate. All of it is measured on the §17 dataset at the default routing, comparing each Fast selection run with the same run with §9 off:
- **Cost:** §9 adds no more than **X%** to the median cost per run.
- **Latency:** §9 multiplies p95 wall-clock time by no more than **Y×**.
- **Budget failures:** at a reference cost limit of **$L**, no more than **Z%** of runs fail as `budget_insufficient` or `budget_exhausted`. A 1-, 3- and 10-file selection must each finish at that limit, which is the "useful answer within a normal limit" check.

**Fallback order.** If the measurements miss the threshold, these are applied in order:
- **F1.** When a claim has **one** citation, skip the separate `critic.citation_relevance` call. The `claim_verify` verdict already judges that citation alone, so nothing is lost.
- **F2.** Fold per-citation relevance into the `critic.claim_verify` call, which then returns the claim verdict **and** one support line per citation, instead of making a separate relevance call.
- **F3.** Raise the verification and relevance batch size from 4 to 8 claims per call.

Each step is measured again before the next is tried. **Any step that changes a prompt or a batch must re-run the G-6 benchmark and still meet D-23**, or it is reverted.

**What a fallback may never do:**
- skip claim decomposition;
- skip verification for any claim;
- re-enable the "verifier failure keeps every citation" behaviour;
- reuse verdicts across a rewrite;
- turn §9 off for selection runs.

**If F1–F3 still miss the threshold,** the release decision goes back to the owner with the measured numbers. The two options are to ship with the measured checking cost and latency stated on the run form and in the release notes, or to hold 3.1.0. Weakening §9 is not an option.

## 16. Migration, recovery, rollback
- **Corpus SQLite.** `_migrate` is additive and idempotent, and runs in one transaction per store. An interrupted migration rolls back and retries on the next open.
- **Legacy desktop store.** Backed up with SQLite's online backup API and verified, then installed by an atomic rename; there is a completion marker and a permanent backup (§7.3).
- **Failed folder import.** A failed import leaves what succeeded. Each file is its own transaction, and the result list says which files failed. A retry is idempotent through duplicate detection.
- **Re-indexing after an embedding-model change.** Duplicate detection blocks it today (audit §5). PR-10 makes the duplicate check model-aware, so a re-upload re-embeds.
- **Rollback.** Downgrading to 3.0.x is supported on read: AC-24 shows legacy documents remain usable. 3.1-only data (folders, new kinds, selections) is invisible to 3.0.x, not corrupted. A server rollback leaves Alembic 0028 in place; its columns are nullable and ignored.

## 17. Evals (write-once results under `backend/evals/results/`)
- **Scoped-retrieval leakage eval.** A new dataset version in `evals/retrieval.py` with non-Markdown fixtures (DOCX, XLSX, CSV, PPTX, code). It measures, per selection, the share of retrieved chunks outside the selection. **The target is exactly 0**, and "unmeasured" is reported as unmeasured.
- **Grounding benchmark (G-6).**
  - **The set.** At least **400** hand-labelled atomic claims, each labelled `supported`, `not_supported` or `contradicted` against its cited snippets. **At least 40% are hard negatives:**
    - a topic-relevant citation that does not support the claim;
    - the right number about the wrong subject;
    - a compound sentence with one invented clause;
    - a claim that needs two sources combined, and one that needs only one of two;
    - rounding and unit traps, and computed values;
    - a conclusion that adds an inference;
    - a fact smuggled into a parenthetical, a table cell or a caption.
  - **Real extracted text.** Claims are drawn from **real extracted text** of every format that ships (Tier A and B at minimum, plus PDF), produced by the shipped extractors, not from clean hand-written text. Labelling is done by a person against the snippet, and the labeller does not see the validator's verdict.
  - **Measured.** On the default checking routing and one local routing:
    - the full 3×3 confusion matrix;
    - **false-accept rate**: share of `not_supported` + `contradicted` claims judged `supported`;
    - **false-reject rate**: share of `supported` claims rejected;
    - `contradicted` recall;
    - the unmeasured share, reported separately, outside the denominator.
  - **Release thresholds** (proposed, the owner confirms at freeze):
    - **false-accept ≤ 2%, with the upper bound of its 95% Wilson interval ≤ 5%.** This is the P0 metric: a false accept is an unsupported claim presented as verified;
    - false-reject ≤ 15%;
    - unmeasured ≤ 5%, or the measurement is invalid and must be re-run, not reported.
  - **Routings that miss the threshold.** A routing that misses the threshold is not blocked. Instead, the run page and the report state *"checker accuracy on this model: below the measured threshold"* (or "not measured" for routings never benchmarked), so a number is never implied where none exists.
  - **The default routing must meet the threshold for 3.1.0 to ship** (§14.2).
  - **Recorded.** The result is committed as `eval-<date>-<routing>-run<N>.json` with the confusion matrix, and the benchmark set is versioned beside it.
- **Before/after for the per-document hit cap** (§9.8), as the same dataset, routing and parallelism. The result is named `eval-<date>-<routing>-run<N>.json`.
- Citation support on selection runs, on the existing harness. Excluding unjudged claims stays the rule (`harness.py::judge_citation_support`, `benchmark.py::calc_support_rate`).
