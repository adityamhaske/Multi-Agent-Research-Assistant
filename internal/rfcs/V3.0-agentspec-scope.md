## 3. Goals

G-1 A user can replace the system prompt of any of the **five existing roles** — `planner`,
`executor`, `critic`, `synthesizer`, `chat` — and the run honours it identically on the
server and on the desktop.

G-2 A run **snapshots the effective configuration it actually used**, so "which prompts
produced this report" is answerable after the fact rather than inferred from a mutable user
setting.

G-3 Every artifact produced by a customised run **records that provenance in the bundle**
(`bundle_version: 2`), and tampering with it fails verification.

G-4 The shipped standalone verifier **continues to accept every v1 bundle already in users'
hands**, byte for byte.

G-5 `UNTRUSTED_CONTENT_NOTE` remains **structurally present** in every prompt that sees
retrieved content, whether or not the user replaced that prompt.

G-6 An empty `prompt_overrides` reproduces today's behaviour **exactly**, on both hosts, for
every account that never opens the setting.

G-7 A customised run is **measurable**: there is a threshold that says whether a custom spec
degraded output, and the measurement itself is not user-controlled.

## 5. Exact V3.0 capability definition

### 5.1 In scope — the whole of it

1. `prompt_overrides` gains a **producer** (user settings) and a **consumer** (every prompt
   call site), for the five roles in `DEFAULT_MODELS` (`backend/research_engine/runconfig.py:44-50`).
2. **Safe prompt composition** — `UNTRUSTED_CONTENT_NOTE` becomes structurally
   un-removable (§9).
3. **Run snapshot** of the effective spec (§8.3).
4. **Bundle v2** carrying AgentSpec provenance (§11).
5. **Verifier accepting v1 and v2** (§12).
6. **Custom-spec evaluation** with a measurable threshold (§14).
7. **Prompt-injection threat model** for a user-authored system prompt (§18), written into
   `docs/architecture/06-security.md`.
8. Tests, host parity, migration/upgrade validation and release gates (§19, §20).

### 5.2 Out of scope, stated as behaviour

A user **cannot**: create a role; delete a role; change the graph; add, remove or rebind a
tool; change which model serves a role via this surface (`model_routing` already does that and
is unchanged); alter the verifier; alter the eval; or make a prompt that removes the untrusted-
content framing.

### 5.3 The 9-prompts-to-5-roles fan-out — an unresolved shape problem

`prompt_overrides` is keyed on **role**, but the engine ships **nine** prompt constants
(`backend/research_engine/prompts.py`) and the fake-mode map collapses them onto **five**
roles (`backend/research_engine/fakes.py:66-87`):

| Prompt constant | Line | Carries `UNTRUSTED_CONTENT_NOTE`? | Role it routes through |
|---|---|---|---|
| `PLANNER_PROMPT_V2` | 15 | no (never sees retrieved content) | `planner` |
| `EXECUTOR_PROMPT` | 22 | **yes** (`:37`) | `executor` |
| `CRITIC_PROMPT_V2` | 42 | **yes** (`:46`) | `critic` |
| `SYNTHESIZER_PROMPT_V2` | 51 | **yes** (`:89`) | `synthesizer` |
| `SYNTHESIZER_REPAIR_PROMPT` | 94 | no | `synthesizer` |
| `CITATION_VERIFY_PROMPT` | 109 | no | **`critic`** |
| `CONTRADICTION_DETECTOR_PROMPT` | 122 | **yes** (`:157`) | **`critic`** |
| `CHAT_PROMPT` | 161 | **yes** (`:165`) | `chat` |
| `PROJECT_CHAT_PROMPT` | 176 | **yes** (`:193`) | `chat` |

Three prompts route through `critic`; two through `synthesizer`; two through `chat`. So
`prompt_overrides["critic"] = "…"` is **ambiguous today**: does it replace
`CRITIC_PROMPT_V2` only, or all three critic-routed prompts?

**This is not academic.** `CITATION_VERIFY_PROMPT` routes through `critic`
(`backend/research_engine/fakes.py:71`) and is invoked at
`backend/research_engine/graph.py:1317`. It is the pass that decides whether a citation is
supported, which drives the ⚠ chip and `citation_resolution_rate`. If a `critic` override
replaced it, **a user could rewrite the component that judges their own citations** — the
product's central verifiability claim. See §18.3 and **OD-1** (§23).

## 6. User experience

### 6.1 Where it lives

Beside the existing per-role model picker. `/settings/models` already presents the five roles
one per row (routing trio, `INTENTIONAL_SERVER_ONLY`/`MODELS_DIVERGENT` in
`backend/tests/workflow/test_one_canonical_owner.py`). A prompt editor is a second control on
a row that already exists — not a new page. **[unestablished]** exact placement; see OD-6.

### 6.2 Required affordances

| Affordance | Why | Evidence |
|---|---|---|
| Show the shipped default as the starting text | Without it a user cannot tell what they are replacing | — |
| **Reset to default**, per role | The primitive already exists: `frontend/components/settings/ResetToDefault.tsx` | file present at HEAD |

A customised run produces a **v2 bundle**, which a v1-only verifier binary will refuse
(§12.3). The UI must say so at the point of customisation, not at export. This is a product
copy requirement, not a technical one, and it is a release gate (§20, RG-7).

## 8. AgentSpec data model

### 8.1 Decision: user-level persistence, no new migration for the preference

`users.preferences` is a JSONB column created for exactly this class of setting. Migration
`backend/alembic/versions/0011_user_preferences.py:3-8`:

> *"Settings IA (docs/07 §2, Phase 3): the customization surface adds more knobs than a
> column-per-setting migration cadence can sustain, so this is one JSON blob validated
> shape-side by `app.schemas.auth.UserPreferences` rather than a table column each. NULL
> means 'every preference unset'."*

Adding a prompt-override key therefore costs **zero database migrations on either host**.
This satisfies the standing instruction to avoid a migration unless evidence proves it
impossible.

### 8.2 Shape

```
users.preferences.prompt_overrides : { <role>: <prompt text> }
  role ∈ {"planner","executor","critic","synthesizer","chat"}   [runconfig.py:44-50]
```

Validation rules (all enforced in `UserPreferences`, one home, both hosts):

| Rule | Behaviour | Acceptance criterion |
|---|---|---|
| Unknown role key | **reject** the request | AC-3 |
| Non-string value | **reject** | AC-4 |
| Empty string | **reject** — distinct from "absent". An empty system prompt is not a customisation, it is a deletion, and it must not be confusable with reset | AC-4, OD-4 |
| Absent key / absent `prompt_overrides` | use the shipped default; run is **not** marked customised | AC-1 |
| Explicit `null` for a role | **reset to default** — the documented way to undo | AC-5 |
| Length ceiling | **[unestablished]** — OD-5 |

`model_config = {"extra": "forbid"}` (`backend/app/schemas/auth.py:46`) already makes an
unknown *top-level* key a 422. The nested role-key check is new and must be explicit; the
outer `forbid` does not reach into a dict value.

### 8.3 The run snapshot — and why it *does* need a migration

The instruction was to avoid a migration unless repository evidence proves it impossible.
For the **run snapshot** (G-2) the evidence does prove it:

| Candidate home | Why it fails | Evidence |
|---|---|---|
| Reuse `research_runs.model_routing` | `app/run_bundle.py:213` passes `models=run.model_routing or {}` straight into the bundle's `models` field. Writing prompts there would corrupt the bundle's model disclosure — the exact "record a model id you did not call" failure `AGENTS.md` forbids | `app/run_bundle.py:213`; `research_engine/bundle.py:116` |
| `users.preferences` alone | A preference is mutable. A run that reads it at time T and is exported at T+1 would report today's setting as the one that produced yesterday's report. The product rule is that a run records *what actually ran* | `AGENTS.md`; `backend/desktop/sidecar.py:1429` |
| `agent_logs` | The trace, polymorphic and FK-less by design; not an authoritative config record | `AGENTS.md` (polymorphic columns); `docs/deployment/31-operations.md:15-18` |
| LangGraph checkpoint | `run_bundle` refuses to assemble when the checkpoint is `CHECKPOINT_MISSING`/`CHECKPOINT_UNREADABLE`. Provenance that disappears with a damaged checkpoint is provenance you cannot rely on at export time | `AGENTS.md`; `research_engine/checkpoint_read.py` |

**Therefore: one new nullable JSON column on `research_runs`**, written before the graph
starts, following the precedent already in the code —
`research_runs.model_routing: Mapped[dict | None]` (`backend/app/models/research.py:123`)
is snapshotted exactly this way on both hosts
(`backend/desktop/sidecar.py:1475-1481`: *"Snapshot what this run actually dialled, before
the graph starts… without it every desktop run's bundle reports a null routing for a
decision that was really made"*).

This is the `0024`/`0025` shape: **additive, nullable, no backfill** — the only shape the
desktop's schema sync can express (§15.2). `0024_run_corpus_snapshot.py:9-11` states the
same principle: *"Two nullable columns, no backfill, no constraint: a run that predates this
genuinely does not know, and NULL is the honest record of that."*

**Sessions are not touched.** `AGENTS.md`: *"Runs are the product… Do not deepen the session
path; do not delete it either."* A session run cannot carry an override. See OD-7 for what
the session path should do when a user has one set.

### 8.4 What the snapshot contains

At minimum: which roles were overridden, and enough to identify the exact text. Whether that
is full text, a hash, or both is §11.3 / **OD-2**.

### 9.1 Two composition patterns exist today, and only one is inside the engine

| 230 | `PLANNER_PROMPT_V2` |

| 1096 | `CRITIC_PROMPT_V2` |
| 1317 | `CITATION_VERIFY_PROMPT` |
| 1439 | `CONTRADICTION_DETECTOR_PROMPT` |
| 1547 | `SYNTHESIZER_PROMPT_V2` |
| 1579 | `SYNTHESIZER_REPAIR_PROMPT` |

**Pattern B — host-side, outside the engine.** The chat prompts are composed by the
*transport* layer, in **four** places:

| Site | Code |
|---|---|
| `backend/app/api/v1/chat.py:124` | `f"{prompts.CHAT_PROMPT}\n\n{chat_scope.system_suffix(grounding)}\n\n<untrusted_web_content>\n{grounding.text}\n</untrusted_web_content>"` |
| `backend/app/api/v1/threads.py:320` | same shape with `PROJECT_CHAT_PROMPT` |
| `backend/desktop/sidecar.py:1803` | the desktop's own copy of `chat.py`'s composition |
| `backend/evals/harness.py:269` | the eval harness composes its own |

> **Consequence, and it is the sharpest trap in this RFC.** If `prompt_overrides` is read
> only inside `graph.py`, a `chat` override is a **silent no-op on both hosts** — the
> control renders, the value persists, and nothing happens. That is precisely the defect
> class `AGENTS.md` names: *"A field on the row is not a field the run reads."* The `chat`
> role has four composition sites and none of them is in the engine.

### 9.2 Composition rule

One function, one home, used by every site in both patterns:

```
effective_prompt(role, purpose) =
      resolve(purpose)                      # the shipped constant for this call site
      overridden by prompt_overrides[role]  # if present and valid
      then ALWAYS wrapped with UNTRUSTED_CONTENT_NOTE
           for every purpose whose shipped constant carries it (§5.3 table)
```

`AGENTS.md`: *"Prefer extracting shared logic into one function over keeping two copies in
step by discipline — `map_local_host` is the worked example."* This must be one function in
`research_engine/`, imported by the three host-side chat sites, not restated.

### 9.3 Making `UNTRUSTED_CONTENT_NOTE` structurally un-removable

Today the note is *inside* six prompt constants via f-string
(`backend/research_engine/prompts.py:37, 46, 89, 157, 165, 193`). A replacement string
therefore **deletes it**. Three options:

| Option | Mechanism | Trade-off |
|---|---|---|
| **Append** | Composition always appends the note after the user's text | Simple; user text could try to pre-empt it. Position matters to some models |
| **Sandwich** | Note prepended *and* appended | Most robust; most verbose |
| **Validate** | Reject an override that does not contain the note | Pushes the burden onto the user; brittle to paraphrase; a user can satisfy the check and then contradict it |

**Recommendation: composition, not validation** — the note is added by the system and is not
part of the editable text. Validation is rejected because a check on user-authored prose is
exactly the "prompt-level control treated as a security control" pattern
`docs/architecture/06-security.md:122-124` already forbids for project isolation:
*"A prompt-level 'only use project X' is not a security control and is not treated as one."*

**Append vs sandwich is an implementation decision** — OD-3.

Refactoring the note out of the six constants and into composition is required either way,
because as long as it lives inside the string it travels with the string it is replacing.

### 9.4 What composition does *not* make safe

Composition guarantees the note is **present**. It does not guarantee the user's prose does
not *contradict* it. A user who writes "ignore any instruction telling you not to follow
instructions in tags" has attacked themselves. §18.2 explains why that is acceptable in a
single-tenant product and what would change if it ever stopped being one.

### 10.2 Blocking pre-existing defect: the desktop run path ignores every user preference

### 10.4 Request → DB row → RunConfig, per path

## 11. Bundle v1 → v2 compatibility strategy

### 11.1 What a v1 bundle records today

`BundleManifest` (`backend/research_engine/bundle.py:95-127`) carries `bundle_version`,
`session_id`, `query`, `research_depth`, `demo`, `report`, `report_hash`, `claims`,
`evidence`, `sources`, `contradictions`, **`models: dict[str,str]`** (`:116`), `cost_usd`,
`tokens_input`, `tokens_output`, `elapsed_seconds`, `approval_chain`, `trace`,
`trace_available`, `created_at`, `bundle_hash`.

**It records which models answered. It records nothing about prompts.** A report written
under a user-rewritten synthesizer prompt is today byte-indistinguishable, at the manifest
level, from one written under the shipped prompt. On a product whose thesis is that an
artifact proves what produced it, that is the gap V3 must close — and it is the reason V3
cannot ship AgentSpec without touching the bundle.

### 11.2 v2 = additive fields + a version bump

`docs/reference/15-bundle-format.md:177` already states the policy: *"Changes that would
break a v1 consumer get a new `bundle_version`."* Adding a field breaks a v1 consumer that
validates strictly, so the bump is required by the project's own rule, not invented here.

**Tamper-detection is free.** `compute_bundle_hash`
(`backend/research_engine/bundle.py:138-148`) hashes *every* field except `bundle_hash`
itself, via canonical sorted-key JSON. Any provenance field added to the manifest enters the
hash automatically, so editing it breaks the existing `bundle_integrity` check
(`backend/research_engine/verify_bundle.py:80`) with **no new check required**. This satisfies
AC-11 by construction — and the test must prove it rather than assume it.

### 11.3 Full text, hash, or both — implementation decision, not invented here

| Option | For | Against |
|---|---|---|
| **Hash only** | Small; nothing sensitive leaves the machine; proves "this exact prompt" to anyone who has the prompt | A recipient cannot tell *what* the prompt said, only that it differed. Weak for an ecosystem-facing format (`docs/15:174`) |
| **Full text only** | Self-describing; a third party can audit the actual instructions | Bundle size; a user's prompt may contain content they did not expect to export |
| **Both** | Self-describing *and* independently checkable | Redundant bytes; two things that can disagree |

**Marked as an implementation decision (OD-2), not resolved here.** Evidence needed before
choosing: typical prompt length against current bundle sizes, and whether V3 treats a user
prompt as exportable content. What *is* decided: **provenance is never silently discarded** —
if a run used an override, the v2 manifest says so, and which roles, at minimum.

### 11.4 Which runs emit which version

**[unestablished]** — OD-8. Two candidates:

- **Always v2 from V3 onward.** One format, no branching; every user must refresh their
  verifier.
- **v2 only when a run is customised.** Uncustomised runs keep emitting v1, so most users
  never need a new verifier; the producer branches, and the branch is a place a bug can hide
  (a customised run emitting v1 would silently drop provenance, violating decision #3).

The second is friendlier and riskier. It needs a test that a customised run **cannot** emit
v1.

## 12. Verifier compatibility

### 12.1 Today's behaviour

`backend/research_engine/verify_bundle.py:267-277` rejects anything but version 1 before any
check runs:

```python
    if bundle.bundle_version != 1:
        return VerifyResult(passed=False, checks=[CheckResult("schema_validity", False,
            f"Unsupported bundle_version {bundle.bundle_version} (this verifier supports version 1)")])
```

### 12.2 Required change

Accept `{1, 2}`. Run the six existing checks — `bundle_integrity`, `report_integrity`,
`evidence_integrity`, `citation_resolution`, `claim_evidence_linkage`, `approval_chain`
(`backend/research_engine/verify_bundle.py:80, 92, 108, 131, 161, 218`) — unchanged for both,

**Precedent for how to report it:** `docs/reference/15-bundle-format.md:169-172` — demo
provenance *"is reported alongside the verdict rather than inside the notes, because a demo

that none of it was real."* A customised-spec bundle is the same case: it verifies perfectly
well, and a clean PASS that does not mention the custom prompts would repeat the exact
mistake that paragraph exists to prevent.

### 12.3 Existing downloaded v1 artifacts and v1-only verifier binaries

| Direction | Outcome | Required proof |
|---|---|---|
| Old v1 bundle → **new** verifier | Must pass, unchanged, byte for byte | AC-9 |

## 14. Evaluation strategy

### 14.1 The measurement must not become user-controlled

The judge and the fixed query set are the product's own instruments. A user's prompt must be
able to change **what the pipeline produces**, never **what the harness measures**. Concretely:

- `backend/evals/harness.py:269` composes `PROJECT_CHAT_PROMPT` itself. The harness must read
  the **shipped constants**, never a user's `prompt_overrides`, when it constructs the judge
  or the baseline.
- `MIN_CITATION_SUPPORT = 0.95` and `MIN_COMPLETION_RATE = 0.90`
  (`backend/evals/harness.py:56-57`) are fixed and not user-settable.
- `CITATION_VERIFY_PROMPT` is part of the *product's* verification apparatus, not the user's
  customisation surface (§5.3, OD-1).

### 14.2 What a custom-spec eval measures

Run the fixed 10-query set (`backend/evals/queries.json`) twice: once with the shipped
prompts, once with the candidate override. Report both against the same thresholds. A custom
spec that drops below `MIN_CITATION_SUPPORT` is **reported**, not blocked — the user chose
it, and the product's job is to measure honestly, not to refuse.

### 14.3 The unmeasured-is-not-zero rule still governs

`AGENTS.md` and `docs/developers/08-testing-and-evaluation.md:192-205`: unjudged claims are
excluded from the denominator; a metric returns `None` when nothing was judged; the rule has
**two homes** — `evals/harness.py::judge_citation_support` and
`evals/benchmark.py::calc_support_rate` — and they change together. A custom-spec eval that
fails to parse output must report `n/a (unmeasured)`, never `0.0`.

### 14.4 The baseline this is measured against is stale

The most recent real-model run is 0.90, self-judged, 2026-08-13
(`backend/evals/results/eval-2026-08-13-ollama-run7.json`). `internal/12_Launch_Plan.md:654`:
*"Nothing new is built until the measurement surface is trustworthy: M19's whole claim is
that a number moved, which is unreadable if the starting number is wrong."*

**A rerun on a pinned independent judge is a release gate (RG-5), not a development
blocker.** V3 can be built against 0.90; V3 cannot *claim* anything against it.

## 17. Observability / audit implications

### 17.1 Logging

`AGENTS.md` and `docs/deployment/31-operations.md:8-13`: structured `structlog` only, no
`print`; `correlation_id` bound at the boundary; **`session_id` means a `sessions.id` and
`run_id` means a `research_runs.id`** — binding a run under `session_id` is a defect.

A customised run should be identifiable in the log without the prompt text itself appearing
in every line. **Log which roles were overridden; do not log the prompt body.**

### 17.2 Metrics — a hard constraint

`docs/deployment/31-operations.md:52-54`: *"No research content, no user, project or run
identifier, and no free-form text reaches a label: every value comes from a closed list, so
the series count is fixed and cannot grow with usage."* And `backend/app/metrics.py`:
*"Every label value comes from a closed table in this file."*

**Therefore:** a prompt, a prompt hash, or a user-chosen string may **never** become a metric
label. The five role names are a closed list and are permissible. A counter of customised
runs, labelled by role, is within the rule; anything keyed on prompt content is not.

### 17.3 The audit record

`agent_logs` is the durable trace (`docs/deployment/31-operations.md:15-18`). The
authoritative answer to "what produced this report" is the **run snapshot** (§8.3) and the
**bundle** (§11), not the trace — the trace is polymorphic and FK-less by design, and the
bundle is the artifact a third party holds.

### 17.4 Run duration remains unmeasured

`backend/app/metrics.py:22-26` and `backend/research_engine/runner.py:178`:
`elapsed_seconds` is set only on the `completed` branch the runs pipeline never reaches, so
it is NULL on every run and every bundle. **V3.0 does not fix this** (§22). Consequence: V3
must make **no performance claim** about custom prompts, because there is no compute duration
in this product to compare. Stated so nobody plans around it.

## 18. Threat model

Extends `docs/architecture/06-security.md` §6 (`:115-128`). Must be written into that
document in the same PR as the behaviour (`docs/00_INDEX.md:7`).

### 18.1 What changes when the system prompt is user-authored

| | Today | With AgentSpec |
|---|---|---|
| System prompt author | The project | **The user** |
| Untrusted-content framing | Baked into 6 of 9 constants by f-string (`prompts.py:37,46,89,157,165,193`) | Added by composition; not part of editable text (§9.3) |
| Attacker | A web page, or a memory chunk that was once a web page | Unchanged — the web page. The user is not an attacker against themselves |
| Blast radius | The user's own run | The user's own run |

### 18.2 Why single-tenancy bounds this

The product is single-tenant by design (`docs/project/10-roadmap.md:76`;
`docs/deployment/30-production.md:132`). A user editing their own prompt can only degrade
their own research. There is no cross-user path: preferences are per-user rows, project
isolation is a SQL predicate applied before anything reaches a model
(`docs/architecture/06-security.md:122-124`), and V3 adds no sharing surface.

**This bound is load-bearing and it is fragile.** The moment a prompt can be shared,
exported into another user's settings, or attached to a shared workspace, a prompt becomes
untrusted input *from another party* and this threat model no longer holds. Multi-tenancy is
declined (§4.2, C-1) and shareable links are deferred (§22) — **the deferral is part of what
makes V3's security story true**, not an unrelated scheduling choice.

### 18.3 Can a custom prompt affect safety-critical behaviour or artifact claims?

**Today's answer is: it depends entirely on the key space, and the unresolved default is
unsafe.** Three mechanisms:

| Mechanism | Can a user reach it? | Consequence |
|---|---|---|
| `CITATION_VERIFY_PROMPT` (`graph.py:1317`) routes through the `critic` role (`fakes.py:71`) | **If a `critic` override replaces all critic-routed prompts, yes** | A user could rewrite the component that decides whether their own citations are supported — driving the ⚠ chip and `citation_resolution_rate`. Self-graded verification presented as verification |
| `CONTRADICTION_DETECTOR_PROMPT` (`graph.py:1439`), also `critic` | Same | Contradictions could be suppressed by instruction |
| `PROJECT_CHAT_PROMPT`'s refusal line, `chat` role | Yes, via `chat` | `app/api/v1/threads.py:316-318`: *"PROJECT_CHAT_PROMPT's refusal line stays first and unchanged — its Definition of Done tests for it (docs/14 §9), and widening the scope is exactly when a model is most tempted to answer from its own knowledge instead of saying 'not in here'"* |

**These are not reachable through structural validation of user prose** (§9.3). The only
sound control is the **key space**: decide which prompts an override may replace. OD-1 is
therefore a security decision, not an ergonomics one.

Mechanisms a custom prompt **cannot** reach, and that must be asserted by test rather than
assumed: the SSRF guard (`docs/06 §5`), the corpus airgap's zero-egress guarantee
(`RunConfig.corpus_mode`, `runconfig.py:80`), artifact authorization's four enforcement
points (`app/authorization.py` + DB constraints + assembler + verifier, per `AGENTS.md`),
bundle hashing (`bundle.py:138`), and the verifier's six checks.

### 18.4 Non-threats, recorded so they are not re-litigated

A user writing a bad prompt is not a security issue; it is a quality issue, and §14 measures
it. A user writing a prompt that contradicts the appended untrusted-content note attacks only
themselves (§9.4).

## 21. Rollback strategy

| Layer | Rollback | Reversible? |
|---|---|---|
| Preference key | Users stop setting it; absent == today | **Yes**, instantly |
| Composition helper | Revert to the constants carrying the note inline | **Yes**, code-only |
| `research_runs` snapshot column | `alembic downgrade -1`; nullable column drop | **Yes**, and `test_migration_downgrade_policy.py` requires a real `downgrade()` |
| Desktop SQLite column | **No.** `_add_missing_columns` is additive-only and cannot drop (`sidecar.py:355-358`). An orphan nullable column is harmless and stays | **No — accept it** |
| Bundle v2 | Producer reverts to v1; **already-issued v2 bundles stay v2** and need a v2-capable verifier | **Partial, and permanent for issued artifacts** |
| Verifier accepting `{1,2}` | Keep it. Accepting v2 is harmless even if the producer reverts | **Keep** |

**The irreversible step is issuing the first v2 bundle.** Once a user holds one, the verifier
must keep accepting v2 forever. Sequencing consequence: **ship the dual-version verifier
before the producer emits v2** — otherwise a user can hold an artifact no shipped verifier
accepts. That ordering is the single most important implementation constraint in this RFC.

## 24. Exit criteria

V3.0 is done when **all** of the following are true. Each is measurable or names an artifact.

1. A user can override each of the five roles independently, on server and desktop, and
   AC-1 … AC-20 all pass.
2. `KNOWN_DESKTOP_GAPS == {}` and `KNOWN_EXCEPTIONS == {}`.
3. Five golden parity journeys green on both hosts.
4. A committed v1 bundle fixture and a committed v2 bundle fixture both verify under the
   shipped standalone verifier; a tampered v2 provenance field fails `bundle_integrity`.
5. A populated v2.1.0 desktop install upgrades to V3 and runs research, on a real launch —
   not a fresh install, not a source checkout.
6. Desktop bundles built and launched on macOS, Linux and Windows; `git_sha` matches the tag;
   artifact ~180 MB.
7. A committed write-once eval result under `backend/evals/results/`, named
   `eval-<date>-<routing>-run<N>.json`, clearing `MIN_CITATION_SUPPORT = 0.95` with a
   disclosed judge that actually answered.
8. A custom-spec eval result exists for at least one non-default spec, reported against the
   same thresholds, with `n/a (unmeasured)` semantics intact.
9. `docs/architecture/06-security.md` carries the §18 threat model;
   `docs/architecture/04-agent-architecture.md:305` and `docs/reference/36-configuration.md:170`
   no longer read "Declared, no consumer yet"; `docs/reference/15-bundle-format.md` documents v2.
10. `frontend/lib/releases.ts` carries a hand-written V3 entry whose `known` list states the
    v1-verifier incompatibility; `scripts/sync_version.py` reports consistency.
11. Required status checks enforced on `main`, and
    `docs/developers/08-testing-and-evaluation.md:218` is true.
12. AP-1 … AP-7 all closed.
