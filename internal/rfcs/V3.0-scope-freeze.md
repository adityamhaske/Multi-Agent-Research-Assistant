## 1. The contract

**V3.0 is:** a user may replace the system prompt of the five shipped agent roles. Every resulting artifact remains verifiable and records the configuration that produced it.

> **Prompt customization changes model behavior, not control-plane security boundaries.**

## 4. Protected purposes — FROZEN

```
critic.citation_verify          drives the ⚠ chip and citation_resolution_rate
critic.contradiction_detector   an override could instruct "report no conflicts"
synthesizer.repair              rewrites citations — D-1
chat.project                    the refusal line is load-bearing (threads.py:316)
```

**Why this list exists at all.** Three distinct prompts resolve through the single role literal `"critic"` (`graph.py:1102`, `:1305`, `:1445`), traced from the AST rather than inferred from names. A role-keyed override resolved at `get_llm`/`_structured` level would reach all three. The purpose classification is the only sound control; validating user prose is not (§6).

### D-1 — `synthesizer.repair` is PROTECTED

`SYNTHESIZER_REPAIR_PROMPT` rewrites citations on a draft. A user prompt replacing that internal repair instruction could cause **fabricated citations to appear repaired**, which would undermine the citation-verification contract from inside the pipeline that produces the artifact.

**Therefore the user-facing `synthesizer` editor customizes report drafting only.**

Accepted consequence, recorded rather than discovered later: a user who rewrites the synthesizer still gets the shipped repair prose, which may read as tonally inconsistent with their own instructions. That is the correct trade — a stylistic seam is preferable to a forgeable citation.

## 5. Prompt composition invariant — FROZEN

```
effective(purpose) =
    NOTE  ⊕  body(purpose)  ⊕  NOTE        if purpose carries UNTRUSTED_CONTENT_NOTE
    body(purpose)                          otherwise

body(purpose) = override[role_of(purpose)]   if purpose ∈ OVERRIDABLE and set
                shipped_constant             otherwise
```

The NOTE is concatenated **by the system**. It is not part of the editable text, is not user-reachable, and is never validated for.

**Measured note placement today** (offset within each constant): `EXECUTOR_PROMPT` 74%, `CRITIC_PROMPT_V2` 41%, `SYNTHESIZER_PROMPT_V2` 86%, `CONTRADICTION_DETECTOR_PROMPT` 87%, `CHAT_PROMPT` 54%, `PROJECT_CHAT_PROMPT` 88%. **The note is never at the head, and in three of six it is followed by further instructions.**

So sandwiching is a deliberate behavioural change, not a refactor — stated plainly because PR-3 must prove byte-identical *behaviour* through the goldens while the composed string legitimately differs from today's interleaving.

---

## 6. Why validation is not an isolation boundary

A check that a user's prompt "contains the note" is satisfiable by text that then contradicts it. `docs/architecture/06-security.md:122` already refuses this exact pattern for project isolation: *"A prompt-level 'only use project X' is not a security control and is not treated as one."* Validating prose would repeat that mistake in a new place. The isolation boundary is **composition plus the purpose classification**, never the content of what a user typed.

## 7. Persistence and validation — FROZEN

### Storage

```
users.preferences.prompt_overrides : { <role>: <string> }   JSONB — NO MIGRATION
research_runs.<new nullable JSON column>                    ONE additive migration
```

User-level (D-6/OD-6). `users.preferences` is JSONB precisely so the customization surface needs no column-per-setting cadence (`0011_user_preferences.py:3-8`). The **run snapshot** is separate and required: a preference is mutable, and a run must record what actually ran. It mirrors `model_routing`'s snapshot (`app/models/research.py:123`), is written before the graph starts, and is nullable with no backfill — the `0024`/`0025` shape the desktop's additive-only sync provably handles.

### D-2 — length limit: **2,500 characters per role**

| Rule | |
|---|---|
| Measured **after** receiving the user value | |
| `> 2500` | **reject** |
| empty or whitespace-only | **reject** |
| Scope | **per role — there is no total five-role limit** |
| Error | **identical on server and desktop** |
| Shipped defaults | **not subject to this validation limit** — it constrains user input only |

Rationale from measurement: the largest shipped prompt is `SYNTHESIZER_PROMPT_V2` at **2,431 chars**, so 2,500 lets a user replace a shipped prompt at approximately the same scale. Context is not the binding constraint — five roles at 2,500 adds ~3,125 tok, which is 1.56% of the smallest catalog context window (200,000). Bundle size is the binding constraint, and 2,500 is the low end of the engineering-safe range, which is the pairing D-3 assumes.

### Full validation table

| Input | Result |
|---|---|
| key absent · `prompt_overrides` absent · `{}` | shipped default; run **not** marked customised |
| `null` | **reset** that role to default |
| `""` | **REJECT** — an empty system prompt is a deletion, not a customisation |
| `"   "` / whitespace-only | **REJECT** — validated after `.strip()` |
| non-string (int, list, dict, bool) | **REJECT** |
| unknown role key (`"researcher"`, `"citation_verify"`) | **REJECT**; the error names the five valid roles |
| known role, `len > 2500` | **REJECT** |
| `prompt_overrides` not an object | **REJECT** |

Rejections are 422 with an identical body on both hosts. `UserPreferences.model_config = {"extra": "forbid"}` (`app/schemas/auth.py:46`) covers unknown **top-level** keys only; the nested role-key and length checks are new and must be explicit.

## 8. Sessions — FROZEN (Option B)

**Invariant: there must never be a silent prompt-override no-op.**

A session started through the legacy session path runs with shipped defaults, and the session row/response carries a machine-readable flag stating that configured overrides were **not applied**; the UI surfaces it.

Refusing the run was rejected — it changes behaviour on a path `AGENTS.md` says not to deepen, and breaks a working control for a user who set an unrelated preference. Implementing sessions was rejected — sessions have their own bundle route, their own two builders and their own desktop driver, which is a second full implementation for a pipeline the product does not offer.

## 9. Bundle v2 — FROZEN (D-3)

**Every V3 run emits `bundle_version: 2`. No conditional emission.** A branch where a customised run can emit v1 is a branch that silently drops provenance.

The v2 manifest records, for each applicable AgentSpec role/purpose as defined by §3:

```
effective_prompt          the full effective prompt text
effective_prompt_sha256   SHA-256 of that exact text
```

The full text makes the artifact **self-describing**, which `docs/reference/15-bundle-format.md:174` requires of an ecosystem-facing format. The hash makes provenance **independently tamper-evident**.

**The hash is included in the existing bundle hash calculation.** `compute_bundle_hash` (`research_engine/bundle.py:138-148`) already hashes every field except `bundle_hash` itself, so both new fields enter it automatically and tampering breaks the existing `bundle_integrity` check with no new check required. A test must **prove** that rather than assume it.

### Artifact-size trade-off — recorded, not estimated

Measured: the bundle in the golden run journey (`tests/parity/golden/research-run.json`) is **11,517 bytes** — a *scripted* run with 8 claims, 8 evidence, 2 sources and a 1,652-char report. Against that baseline, worst case (all five overridable roles customised at 2,500 chars) adds ≈13,225 bytes of text plus ≈420 bytes of hashes.

**No real-model bundle is committed to this repository, so the production ratio is unknown and is deliberately not estimated here.** A production bundle carries far more evidence, so the proportional overhead is lower — by how much is unmeasured. Precedent: `BundleManifest.query` already carries the user's own prompt, so user-authored text in a bundle sets no new privacy precedent.

## 10. Verifier compatibility — NON-NEGOTIABLE ORDERING

`research_engine/verify_bundle.py:267` currently hard-rejects `bundle_version != 1`. V3 must accept `{1, 2}`, run all six checks unchanged for both, and report AgentSpec provenance **alongside** the verdict — the precedent at `docs/15:169` for demo provenance, where a clean PASS that fails to mention the caveat is the exact failure that paragraph exists to prevent.

> **The dual-version verifier ships before any producer emits v2.**

Existing v1 bundles remain valid forever. Verifier binaries already downloaded will refuse v2 permanently; that is unavoidable and must be stated in the release notes and at the point of customisation.

**One correction worth recording, because it was not requested.** GitHub creates a
`pull_request` rule with `require_extra_approval_for_unattributed_changes: true` by default.
That silently reintroduces an approval requirement on exactly the changes most likely to
appear here — commits carrying co-author trailers — which contradicts the deliberate choice
of **0 approvals** and automated gates over a human bottleneck. It was set to `false` and
re-read to confirm. A ruleset created through the UI will have it on unless it is turned off.

**Why these eleven and not the others.** Every required check runs on `pull_request` and
none carries a job-level `if:`, so none can be skipped into a permanent block — verified
against `ci.yml` and `desktop.yml` before enforcement. The excluded set is excluded for
reasons, not taste: the four CodeQL `Analyze (...)` contexts and `CodeQL` are informational;
`Publish release` is tag-conditional and reports `skipped` on every ordinary commit, so
requiring it would deadlock every PR; `Pages` is path-filtered to `frontend/**` and `docs/**`
and would deadlock any PR touching neither; `update-pip-graph` is dependency-graph only.

**Confirmed on a live pull request** (#158, `v3-preparation` → `main`): `mergeStateStatus`
came back `BLOCKED` while checks were outstanding, and GitHub's own required/informational
split put the eleven in `isRequired: true` and every `Analyze (...)` context in
`isRequired: false`.

**The consequence, stated plainly.** With no bypass actors, a broken CI freezes `main`
outright. There is no admin escape hatch by design; recovery means editing the ruleset.
That is the trade this configuration makes deliberately.

### D-6b — answered

`enforce_admins` was a classic-protection field and no longer exists here. The ruleset
equivalent is the bypass list, and it is empty: GitHub reports `current_user_can_bypass:
"never"` for the repository owner. Branch protection binds everyone.

## 12. UI contract — Settings → Models

Five role editors on the existing per-role rows. No new page, no per-run override. Shipped default shown as the starting text. Reset-to-default per role via the existing `ResetToDefault.tsx`, emitting `null`. Validation errors surfaced inline with the same text the API returns. **Empty or whitespace is not a valid custom prompt** — the UI must not present "clear the box" as reset. **Protected purposes are never exposed**: no mention of `citation_verify`, `contradiction_detector`, `synthesizer.repair` or `chat.project`. A customised role is visibly marked, and the surface states that customisation is recorded in the exported artifact and that v2 bundles require a refreshed verifier.

## 15. Acceptance criteria added or changed by these decisions

| ID | Criterion |
|---|---|
| **AC-D1a** | An override set for `synthesizer` changes `synthesizer.main` only; the composed `synthesizer.repair` prompt is byte-identical to the shipped constant |

| **AC-D3c** | `effective_prompt_sha256` equals SHA-256 of `effective_prompt` |
| **AC-D3d** | Mutating either field breaks `bundle_integrity` — proved, not assumed |
